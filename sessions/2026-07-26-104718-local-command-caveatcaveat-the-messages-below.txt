⏺ I read through the whole pacman demo. Your diagnosis is right, and the cause
  is specific — it's not a training problem, it's a feature problem. Let me show
  you exactly where.

  The smoking gun

  Every spatial signal pacman has is straight-line distance, computed as if 
  walls don't exist:

  - pacman.wgsl.ts:178 nearestPelletDist → sqrt(dx*dx + dy*dy)
  - pacman.wgsl.ts:195 pelletPotential → Σ 1/(1 + |dx| + |dy|)
  - pacman.wgsl.ts:290-306 the pelletVec NN input → unit vector to the
  Manhattan-nearest pellet

  And at pacman.wgsl.ts:383:

  wgsl
  sum += clamp(distGain * 2.0 + fieldGain * 35.0, -2.0, 6.0);

  That 35.0 multiplier makes the potential field ~10x stronger than anything the
  network outputs. When ghosts are gone, that hardcoded field is the policy —
  the net isn't driving anymore. (It activates on nearestThreatD > 100.0, and
  eyes-mode ghosts don't count as threats, so "all ghosts gone" is precisely
  when it takes over.)

  Why that produces walk-back-and-forth specifically

  A wall-blind attraction field over a maze has local maxima inside wall blocks.
  With a scattered handful of pellets left, the field's gradient points
  diagonally through a wall. Both perpendicular neighbors have near-identical
  fieldGain (≈0), so the choice is decided by a tiny noisy difference. Pacman
  steps left → the right-side pellets are now marginally closer → gradient flips
  → steps right. That's a stable two-tile limit cycle, and it's smooth, not
  jittery — exactly what you described.

  Same defect in distGain: walking around a wall block to reach a pellet
  temporarily increases straight-line distance, so the term actively punishes
  the only correct path.

  The reversal penalties (A_REVERSAL_STREAK, pacman.wgsl.ts:469), the +0.2
  inertia bias, and avoidReverse are all band-aids over this — they suppress the
  symptom while the underlying field still points into a wall.

  The fix: real maze distance

  The maze is static, so precompute it once on the CPU and never pay for it
  again. I verified the numbers:

  - 318 walkable tiles, 244 pellet tiles, max path distance 52 (fits in a u8)
  - Full tile→pellet BFS table: 212 KB as packed bytes — one read-only storage
  buffer, uploaded at init
  - (The 18 unreachable tiles are the ghost-house interior; pacman never enters
  it)

  This is cheaper at runtime than what's there now: the current code runs
  nearestPelletDist + pelletPotential over 896 bit-tests with sqrt, five times 
  per tick. Table lookups over 244 pellets × 4 directions is roughly a quarter
  of that work.

  The payoff is a guarantee, not a tuning knob: greedily descending true path
  distance to the nearest pellet cannot oscillate. Distance strictly decreases
  until a pellet is eaten, then targets the next one. It isn't optimal (that's
  TSP), but it always terminates having cleared the board.

  One design call worth making

  While I'm in there, the genome is a linear 16→4 map (PACMAN_TOPOLOGY = [16, 
  4]), so all intelligence must live in the features — the net can't internalize
  maze topology. The higher-leverage version reformulates it as per-direction 
  features with shared weights (score each of the 4 moves with the same ~10
  weights, take argmax): path-distance gain, blocked, pellet density ahead,
  ghost path-distance, scared-ghost attraction, is-reverse. That's
  direction-invariant, so evolution converges much faster and 10 weights replace
  68 — but it changes the genome format and invalidates saved models.

  Where it honestly stands

  It plateaus around 40 pellets ≈ 16% of the board, from roughly gen 10 onward.
  The doc claims 70%. I won't pretend that's a match, though the environments
  aren't comparable — theirs is a 简单地图 with simplified ghosts, ours is the
  full arcade maze, four authentic ghosts, and one life (dead at ~21 s, so they
  never see the late board). I separately measured that a greedy maze-distance
  policy clears all 244 pellets in 30 s, so the environment is solvable; this is
  a learning/representation ceiling, not an environment one.

  The three things I'd point at, in order:

  1. Fitness is one noisy episode. With sampled actions the same genome scores
  wildly differently run to run — note best bouncing 99→187 with no trend.
  That's a lottery, and tournament k=3 on lottery fitness selects mostly noise.
  Averaging 2–3 episodes per genome is the fix.
  2. dirIndex/3 is a categorical variable crammed into one scalar (up=0,
  down=0.33, left=0.67, right=1.0). The net must learn a non-monotonic map from
  that through 6 ReLU units. This is the doc's own encoding, and its §5.2
  concedes 更好的特征表示能让学习事半功倍 — one-hot or a (dx,dy) pair would cost
  2–3 dims and be far more learnable.
  3. One life gives no gradient toward finishing a board.

  watch it in the browser first?

  it's exactly what this project kept teaching us the hard way.

  Selection is one of four levers, not the whole GA

  A GA optimizes whatever fitness measures, over whatever the representation can
  express, using whatever variation the operators can produce — and then
  selection picks winners. Selection can only choose among candidates that
  variation actually generated, within the space representation makes reachable,
  toward the target fitness defines.

  Our own three biggest wins land in three different levers, and none of them 
  was selection:

  ┌─────────────────────┬────────────────┬─────────────────┬───────────────┐
  │         Win         │     Lever      │     Effect      │  Selection    │
  │                     │                │                 │     code      │
  ├─────────────────────┼────────────────┼─────────────────┼───────────────┤
  │ Sealed weight box → │ Variation      │ 40.3 → 68.4     │ unchanged     │
  │  drift mutation     │                │ pellets         │               │
  ├─────────────────────┼────────────────┼─────────────────┼───────────────┤
  │ Ordinal → vector    │ Representation │ 8.5 → 34.0 at   │ not even      │
  │ direction encoding  │                │ generation 1    │ running yet   │
  ├─────────────────────┼────────────────┼─────────────────┼───────────────┤
  │ Removing the        │                │ whole           │ unchanged,    │
  │ Math.max(1, …)      │ Fitness        │ population tied │ but blind     │
  │ clamp               │                │  at 1           │               │
  └─────────────────────┴────────────────┴─────────────────┴───────────────┘

  The sealed weight box is the clearest case. Tournament selection was working
  perfectly the entire time — it just had nothing good to choose from, because
  every candidate that could ever exist was trapped in [-1, 1]. Perfect
  selection over a broken candidate pool gives you the best of a bad set.

  And the writeup's own §3.1 story is the fitness version: with fitness = score,
  selection correctly and efficiently found the optimum, which was standing 
  perfectly still. Nothing was wrong with the selection.

  "Is this game AI or GA?"

  There's a real spectrum, and your instinct is picking up on something true:

  ┌─────────────────┬────────────────────────┬─────────────────────────────┐
  │                 │    What's hand-made    │       What's learned        │
  ├─────────────────┼────────────────────────┼─────────────────────────────┤
  │ Hand-coded bot  │ the whole strategy     │ nothing                     │
  ├─────────────────┼────────────────────────┼─────────────────────────────┤
  │ Ours            │ perception (what it    │ policy (how to weigh what   │
  │                 │ can see)               │ it sees)                    │
  ├─────────────────┼────────────────────────┼─────────────────────────────┤
  │ End-to-end deep │ nothing                │ everything, from pixels     │
  │  RL             │                        │                             │
  └─────────────────┴────────────────────────┴─────────────────────────────┘

  pellets when hunted," or "prefer dense pellet regions" — those weights are all
  discovered. The writeup takes exactly this position in §2.2, arguing for a

  near, flee" has no room to evolve, whereas connection weights do.

  Where you're right: temperature is controller design, not GA. That one is a
  genuine policy knob, and I should label it as such rather than smuggle it in
  as evolution.

  But episode averaging is pure GA machinery. It's not about making pacman
  smarter — it's about the fitness estimate being accurate. Noisy fitness means
  selection selects noise. It's a standard topic in evolutionary computation
  (resampling, common random numbers), completely game-agnostic. So it
  strengthens the case for doing it first, rather than weakening it.

  Each README covers the world and its constants, every input with its
  normalisation and why it exists, output semantics, the genome layout table,
  fitness with the reasoning behind its shape, selection, a file map, and open
  improvements.

  Some things worth surfacing that only came out of reading the code:

  - Dino and flappy share one world across the whole population. Several inputs
  are therefore identical for every agent on a given frame, so generation 1
  moves as a single mass. That's faithful to the originals but genuinely narrows
  the GA's signal — I flagged it rather than describing it as ordinary
  per-agent play.
  - Snake's starvation budget needs no penalty term. 200 moves, +100 per apple,
  capped at 500 — loopers simply run out. That's a cleaner solution than
  pacman's wall-clock stall timeout, and I said so.
  - Snake applies ReLU to its output layer, so several directions can tie at
  exactly 0 and argmax then favours the lowest index. Faithful to the source,
  but it's a real bias worth knowing about.
  - Track strips partial checkpoint credit on a crash. Without it, flooring into
  a wall would bank progress before dying. That's a subtle and deliberate piece
  of design.
  - Track's dynamic elite scaling — once maxFitness ≥ 0.95 it jumps to 50%
  elites and drops mutation from ±1.2 to ±0.2. It's the best idea in the repo
  that nothing else uses, and it's precisely the failure mode pacman hit when
  its mutation rate ratcheted up and never came back.

  I also connected the demos where a fix already exists: snake has the same 
  noisy single-episode fitness that cost pacman a 4× spread, and
  src/utils/evaluation.ts is already shared, so it could adopt it directly.
  That's the highest-value open item across the four.
